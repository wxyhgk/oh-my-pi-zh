# ERRATA — GPT-5 Harmony 头部泄漏

历史研究笔记,并非当前运行时契约。以下统计数据来自指定的本地统计数据库快照,而非检入的测试或运行时代码。

## 当前的运行时缓解措施

当前行为实现在
`packages/ai/src/utils/harmony-leak.ts` 和
`packages/agent/src/agent-loop.ts` 中:

- 对 Harmony 方言模型的请求,在重放前会对不可信文本、工具结果和序列化后的工具参数中的保留 `<|...|>` 拼写进行转义。
- 响应泄漏检测对所有提供商为 `openai-codex` 的模型启用,而不是针对固定的模型 ID 列表。
- 单独的 `to=functions.NAME` 标记并不充分。检测需要共信号(通道相邻、故障 token、脚本不匹配、级联、伪造结果框架,或可信的尾部解析边界);围栏内的示例会被忽略。
- Agent 循环会扫描最终确定的可见文本与思考内容。命中时丢弃部分响应并最多重试两次,然后升级为错误。审计回调会收到动作/信号元数据以及被移除内容的哈希/脱敏预览。
- 工具参数检测刻意保持惰性,除非调用方提供了结构性有效工具解析结束处的字节偏移。主 agent 循环目前不提供该边界,从而避免对讨论协议的合法工具数据产生误中止。
- 对有界自由格式的 `eval` 输入和当前的 hashline `edit` DSL(以 `@` 开头的输入)存在恢复支持:它在受污染行处截断并追加 `*** Abort`。Apply-patch 信封和 JSON-schema 编辑输入不符合恢复条件,在有界检测可用时使用中止/重试。

下面的语料表格描述该快照中存在的历史输入格式;它们不是当前 `edit` 工具所接受语法的清单。

## 1. 问题

OpenAI 在 Harmony 聊天协议中封装工具调用:

```
<|start|>assistant<|channel|>commentary to=functions.<NAME><|message|>{ARGS}<|call|>
```

`<|channel|>commentary to=functions.NAME` 是**路由头** ——
运行时消费以分派调用的控制 token。正常操作下这些
token 永远不会作为内容出现;运行时会剥离它们。

缺陷:gpt-5 模型偶尔会在 `{ARGS}` 内部**作为普通内容**发出这些路由 token 的**纯文本影子** ——
即不带 `<|…|>` 括号的相同字符 —— 并继续生成更多伪路由结构(通道名、正文标记、
多语言垃圾信息、伪造的工具结果框架)。污染位于可见工具参数内部,并被分派给工具,
仿佛它就是预期内容。

**关键细节。** 实际的 `<|start|>` / `<|channel|>` /
`<|message|>` / `<|call|>` 特殊 token 几乎不会出现在工具
参数中。泄漏的是无括号拼写 —— `analysis to=functions.X
code …` —— 因为 OpenAI 应用了 logit 掩码,压制了参数区域内
的控制 token ID。本应流向这些特殊 token 的质量重新分布到
模型同样学到的无括号纯文本表示上。这使得泄漏在结构上对
路由解析器不可见,并原样落入工具输入。

工具参数中的表现(真实语料示例):

```
~      add_function(iso, ctx, ns, "installSystemChangeObserver",
        os_install_system_change_observer);】【"】【analysis to=functions.edit
        code above เงินไทยฟรีuser to=functions.edit code …
```

前导代码是真实且预期的。第一个非拉丁 token 之后到下一个干净结构边界之间的所有内容都是损坏。

## 2. 观测统计与失败模式

来源:`~/.omp/stats.db`(`ss_tool_calls`、`ss_assistant_msgs`),截至
2026-05-10。扫描了 1.05M 次工具调用。

### 2.1 发生率

| 模型           | 工具参数泄漏数 |   调用数 | 每百万次 |
| ------------- | -----------------: | ------: | ----------: |
| gpt-5.4       |                 37 | 226,957 |         163 |
| gpt-5.3-codex |                 17 | 112,243 |         151 |
| gpt-5.5       |                  2 |  80,750 |          25 |
| gpt-5.2-codex |                  0 |       — |           — |

另有 15 次命中出现在助手可见文本 / 思考块中。

### 2.2 工具分布

| 工具                             |   命中数 |
| ------------------------------ | -----: |
| `edit`                         |     38 |
| `eval`                         |     11 |
| `report_tool_issue`            |      3 |
| `grep`/`read`/`search`/`yield` | 各 1 |

集中在具有自由格式(非 JSON-schema)参数格式的工具中。

### 2.3 泄漏形态(确定性)

```
LEAK         ::= JUNK_PREFIX MARKER CHANNEL_BODY (LEAK)?
MARKER       ::= "to=functions." TOOL_NAME
CHANNEL_BODY ::= " code " (SPAM | reasoning_prose | fake_tool_output)*
JUNK_PREFIX  ::= (GLITCH_TOKEN | CHANNEL_WORD | NON_LATIN_RUN | "}" | "】【")+
```

**级联很常见。** 在 71 条受污染记录中的 96 次标记出现中,39 条包含 ≥2 个标记,7 条包含 ≥3 个 —— 模型会连续发出多个伪造的 `to=functions.X code …` 块,且常常在它们之间夹带伪造的 `code_output\nCell N:\n…` 框架。一旦纯文本脚手架进入残差流,前缀现在_看起来像_一个新的工具信封开头,因此对后续内容的宏先验持续投票生成更多脚手架。自我放大。

### 2.4 故障 token

`o200k_base` 中的单 token 标识符,其嵌入向量因在后期训练中代表性不足而似乎接近初始化值。自然语料中紧邻标记之前的 ASCII 残渣:

| 表面字符串        | 单 token | Token ID |                  语料命中数 |
| ----------------- | :----------: | -------: | ------------------------------: |
| `Japgolly`        |      ✅      |  199,745 |                               1 |
| `Jsii`            |      ✅      |  114,318 | (`Jsii_commentary` 的子 token) |
| `Jsii_commentary` |  — (3 个 token)  |        — |                               2 |
| `changedFiles`    |  — (2 个 token)  |        — |                               8 |
| `RTLU`            |  — (2 个 token)  |        — |                               3 |

`Japgolly` 位于词汇表最后 0.13% —— 与 2023 年 GPT-2 词汇表中产生 `SolidGoldMagikarp` 的是同一类 GitHub 语料残渣(Rumbelow & Watkins)。`SolidGoldMagikarp` 本身在 `o200k_base` 中被 token 化为 5 个 token —— 那个特定 token 已被退役,但这一类问题并未消除。

对于多 token 条目,语料级签名是表面字符串;底层故障触发是子 token(例如 `Jsii_commentary` 中的 `Jsii`)。检测器列表(`G` 信号)以表面字符串为键。

跨无关会话保持稳定。被视为高精度检测器信号。

### 2.5 通道词泄漏

`analysis`(5)、`assistant`(5)、`commentary`(3)、`user`(1)直接出现在 `to=` 之前。始终是裸词;从不出现 `<|channel|>analysis` 或任何其他带括号形式。与 §1 一致 —— 括号被掩码,单词没有被掩码。

### 2.6 非拉丁垃圾信息残渣

96 次标记命中,按文字分:CJK 40、西里尔 12、泰卢固/卡纳达/马拉雅拉姆 18、泰文 8、格鲁吉亚 7、亚美尼亚 7、阿拉伯 1。反复出现的片段是中文赌博 SEO(`大发时时彩`、`天天中彩票`)、格鲁吉亚/阿布哈兹垃圾信息,以及泰式赌场垃圾信息 —— 众所周知的低质量爬取残渣。

这与受控复现(§7.3)中观察到的文字分布相同,与提示词的自然语言无关。

### 2.7 `edit` 工具的失败模式细分

`edit` 工具在语料中存在两种变体:

| 变体                                                | 调用数 | 恢复                                                                                                                                             |
| -------------------------------------------------- | ----: | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Patch-DSL(`[PATH#TAG]`/锚点/`SWAP DEL INS` 操作)     |    27 | **可恢复** —— 通过操作截断(§3.3)                                                                                                              |
| JSON-schema(`{path,edits:[…]}`)                   |    11 | **不可恢复** —— 污染被转义到 JSON 字符串_内部_,解析器会干净地接受它,内容会被原样写入源文件 |

具体到 Patch-DSL 泄漏:

- 20/27 例:污染出现在最后一行输入;后面没有内容。
- 7/27 例:污染出现在输入中间;后面是以下之一:更早文件/锚点的重复重放、针对_不同_工具调用的预期内容(模型内联开始了下一个调用),或纯粹幻觉。污染后的内容永远不可信。

### 2.8 机制(已确认)

**先验坍缩:来自空嵌入故障 token,进入控制 token 被掩码的盆地,其质量重新分布到 Harmony 协议的纯文本影子上。**

逐步说明:

1. 模型正处于 Harmony 工具调用的 `{ARGS}` 中间。运行时应用 logit 掩码,压制参数区域内的结构性控制 token(`<|channel|>`、`<|message|>`、`<|call|>`、`<|start|>`、`<|end|>`)。没有这个掩码,正常生成会不断幻觉出信封闭合;有了它,这些 token ID 在参数中 logit 为 `-∞`。
2. 采样到一个故障 token `g`。按构造,`g` 曾在 BPE 合并语料中,但几乎没进 LM/RL 训练,因此其**输入嵌入 `e_g` ≈ 接近初始化的小范数噪声**。
3. 在位置 t+1,残差更新 `h_{t+1} ≈ LN(h_t + e_g + Attn + MLP)` 由前缀派生项主导;刚发出 token 的信号实际上缺失。生成多样性通常来自 `e_x` 将残差引导到不同子区域 —— 这里被剥除了。
4. 因此下一个 token 的分布坍缩到**前缀续写的条件先验上,局部条件被移除**。在工具调用 rollout 语境中,该先验强烈峰值为 Harmony 脚手架(控制 token + 路由 token)—— 这正是 RL 训练出来的。
5. 掩码将控制 token ID 归零。质量重新分布到**次优续写**:同一协议的未加括号表面形式拼写(`analysis`、`commentary`、` to=functions.X`、`code`)。这种拼写未被掩码,因为这些字符是普通 token。
6. 一旦几个纯文本脚手架 token 进入残差流,前缀就类似于新的信封开头。宏先验持续投票生成更多脚手架。随之而来的是级联(§2.3)。
7. 标记之后的多语言垃圾信息是同样的先验坍缩续写,从故障 token 的训练邻域中抽取(通常是 ESL/自动生成的多语言网页垃圾 —— 正是 §2.6 中的爬取残渣)。

**语料数据要求的两个推论,只有实验能解释:**

- **括号从不出现**(§1、§2.5)。正是掩码使泄漏以纯文本形式落地,而不是作为真正的信封闭合。
- **反直觉的语法依赖性**(§7.4)。泄漏在越接近 OpenAI 训练分布的格式中_越严重_。偏离分布的自定义语法会削弱宏先验盆地;官方的 `*** Begin Patch` 格式是最强的坍缩目标。

2023 年的 SolidGoldMagikarp 论文记录了机制 (1)+(2)+(4)。新增的部分是 (5):当受约束解码掩码掉自然的坍缩目标时,经过未掩码纯文本影子清洗出来的质量,就成为结构性不可见的泄露通道。
